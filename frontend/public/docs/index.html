Business Context

GlideGate is an agentic, multi-product client onboarding platform for financial services. It automates the intake, KYC/AML compliance verification, document collection, product suitability assessment, and account provisioning for multiple products — in parallel — while keeping humans in the loop for regulated decisions.

The platform is being generalized into the CADF (Client Agentic Development Framework) — a domain-configurable framework where new onboarding domains (Retail/Deposit, Loans, Mortgage, Wealth) can be configured through an admin portal without engineering changes or redeployment.

Products supported

Wealth Management

Equity funds, bonds, savings accounts. KYC + suitability assessment + Sales Manager approval for institutional products.

Retail / Deposit ✅ Phase 11

Savings, checking, and CD accounts. Configured entirely through the admin portal — zero migration scripts, zero new agent classes. Domain-isolated cases (deposit_ops / branch_manager personas).

Loans Roadmap

Consumer + SME loans. Credit bureau pull + affordability + adverse-action records (ECOA).

Mortgage Roadmap

Home + commercial mortgages. Appraisal + title verification + TRID disclosure timing.

SALES_REVIEW applies only to institutional products (equity funds, bonds). Retail products skip directly from REVIEW → KYC. PARALLEL_PRODUCTS runs one Temporal child workflow per selected product concurrently — the first to meet its activation criteria goes live independently.

First-to-complete go-live ✅ Phase 4.6

When a client selects multiple products, each runs in parallel. The first product to satisfy all its activation criteria — KYC passed, fraud cleared, suitability assessed — is provisioned immediately with an account number. Other products continue in background. The advisor panel shows per-product activation badges (ACTIVATED / DECLINED / PENDING) and a "First Live" highlight on the first product to activate.

Configurable SLA enforcement ✅ Phase 5

Each onboarding stage has a configurable SLA window stored in the domain_stage_slas table, keyed by domain, stage, priority tier, and product. A 4-step priority chain resolves the effective window: (stage + tier + product) → (stage + tier) → (stage + product) → (stage only); the first matching enabled row wins. A row with is_enabled=False short-circuits to no SLA for that combination, enabling per-product or per-tier opt-outs.

When a stage starts, start_sla_tracking_activity writes a case_sla_tracking row and _watch_sla() launches as an asyncio.Task inside the Temporal workflow. It sleeps to the warning threshold (default 70% of window), fires send_sla_warning_activity, then sleeps to the breach threshold (default 90%) and fires trigger_sla_breach_activity — which transitions the case to ESCALATED and writes an SLA_BREACH entry to decision_log with is_regulatory_breach=True (BSA). Warning and breach activities are idempotent — they check warning_sent_at / breach_triggered_at before acting, safe for Temporal retries.

Clock pausing applies to stages with pause_on_human_review=True (REVIEW, SALES_REVIEW). The SLA task is cancelled before wait_condition, paused_at is recorded in the DB, and a new _watch_sla task restarts after the human responds with accumulated elapsed seconds subtracted from the remaining window. The wealth domain is seeded with 8 SLA rows across all 6 active stages (migration 0019).

Document collect-once pattern Phase 4.5

Shared-core documents (Government ID, proof of address, W-9) are collected once and reused across all products that require them. A client never uploads the same document twice. Product-specific documents (investment mandate, loan purpose statement) are collected per-product.

Skills (composable LLM capabilities) ✅ Phase 6

Six composable skills — information extraction, decision reasoning, status summarisation, clarification, escalation, product suitability — are wired into agent LangGraph nodes via domain_agent_skills DB bindings. The EscalationSkill is bound to the KYC agent; it enriches the checkpoint result with LLM-based reasoning but does not override the deterministic CheckpointRuleEngine decision for routing. Skill parameters are configurable per domain row without a code change.

MCP Gateway (ADR-007) ✅ Phase 6

All external integration calls route through MCPRegistry.invoke(), which enforces domain_agent_tool_grants before dispatch — agents that lack a grant row receive a PermissionError (fails closed). The KYC agent calls three tools: verify_identity, check_sanctions, score_aml_risk. Tool grants and agent system prompts are seeded per domain (migration 0020) and overridable via domain_agent_prompts without redeploy.

Authentication & RBAC ✅ Phase 7

All API endpoints are protected by JWT bearer tokens (HS256, 8-hour expiry, also delivered as an httpOnly cookie for browser sessions). Role-based access control is enforced by a configurable permission model backed entirely by the domain_permissions database table — no role strings are hardcoded in application code.

Permission guard

require_permission("scope") is a FastAPI dependency that replaces the old hardcoded require_role() guards across all 11 router files. It queries domain_permissions to check whether any of the user's persona codes has the requested scope, caches the result in-process, and returns HTTP 403 otherwise. A companion has_permission(user, scope, db) → bool helper is available for inline permission checks (e.g. the institutional product gate) without raising.

Multi-role support

A user can hold multiple personas simultaneously via the user_personas(user_id, persona_code) join table (migration 0022). The JWT carries "roles": ["advisor", "compliance_officer"] (full list) plus "role": "advisor" (primary persona, for backwards-compat identity checks). require_permission() grants access if any of the user's personas has the required scope — no code change needed when a new persona is introduced for Phase 11 Retail/Deposit. 

JWT payload:
{
  "sub": "...",
  "email": "advisor@example.com",
  "roles": ["advisor", "compliance_officer"],  // authoritative list
  "role":  "advisor",                          // primary (backwards compat)
  "name":  "Jane Smith",
  "exp":   1750000000
}

Institutional product gate

The GET /cases/products endpoint previously used a hardcoded role != "client" check to decide whether to show institutional or retail products. This is now replaced with: has_permission(sales:review) AND has_permission(case:create) — both scopes must be granted for institutional products to be shown. Sales managers received case:create in migration 0022 to make this explicit.

For domain_products the filter is by exclusion: products with product_type = "institutional" are hidden from non-institutional users; all other types (retail_savings, retail_checking, retail_cd, etc.) are visible. The legacy products table fallback still uses exact-match product_type = "retail".

Domain-scoped case isolation ✅ Phase 11

Migration 0029 adds domain_id (nullable FK → domains.id) to onboarding_cases. Every new case is stamped with the active domain's ID at creation time. GET /cases filters by domain using the JWT roles list joined against domain_personas:

RoleFilter applied
clientWHERE client_id = {sub} (own cases only, any domain)
adminNo filter — sees all cases across all domains
Any other persona (e.g. advisor, deposit_ops)WHERE domain_id IN (domains whose domain_personas includes this persona code)

Existing cases were backfilled with the wealth_management domain ID. A user whose persona is absent from all domain_personas rows receives an empty result rather than full access (fail-closed).

Frontend routing — open persona support ✅ Phase 11

ProtectedRoute was refactored from a hardcoded allowedRoles: string[] check (4 fixed values) to a semantic audience prop:

AudienceAllowedRoutes
staffAny role that is not client/, /contact-centre, /agent-trace
clientclient only/client
adminadmin only/admin
anyAny authenticated user/profile

AuthUser.role was widened from a 4-value union to string so domain-configured personas (e.g. deposit_ops) can be stored without TypeScript errors. Post-login redirect derives the destination from role semantics rather than a hardcoded map: client → /client, admin → /admin, all others → /. A /advisor/* catch-all redirect handles nav_links already stored in the DB that use /advisor/cases hrefs.

Permission cache & invalidation

Results are cached in-process as (frozenset[persona_codes], scope) → bool. The cache is cleared on application startup and will be invalidated by the Phase 9 admin portal after bulk permission edits. Negative entries (False) are safe — they cannot be promoted by a user request; only a server restart or explicit clear_permission_cache() call can change them.

Domain config API & persona-driven frontend ✅ Phase 10

GET /config/domain returns the full active-domain configuration in a single response: persona list (with nav_links, color, default_route), stage list, and product list. The frontend useDomainConfig hook consumes this endpoint on mount; App.tsx replaces its static _STATIC_NAV and ROLE_HOME constants with the persona data from the API. Persona nav links stored in domain_personas.nav_links (JSONB) are seeded per-role by migrations 0026 and 0027 — advisor and sales_manager see Workspace / Agent Trace / Contact Centre; admin sees Agent Trace / Admin; client sees no tab bar.

The MultiFormWizard and OnboardingWizard product selectors now read from the active domain's domain_products table instead of the legacy products table. When a domain is deactivated its products immediately disappear from the wizard (React Query cache is invalidated on activate/deactivate). Case creation accepts domain product codes via _resolve_products(), which checks domain_products first and falls back to products for legacy rows; case_products.product_id is nullable (migration 0025) so domain products with no legacy FK can be stored.

Domain-authoritative stage validation ✅ Phase 8

Migration 0023 drops three hardcoded DB CHECK constraints that encoded the wealth-domain vocabulary directly in PostgreSQL:

Constraint droppedTable · ColumnReplaced by
oc_status_chkonboarding_cases.statusContextStoreService._validate_stage() queries domain_stages
oc_stage_chkonboarding_cases.current_stage
products_type_chkproducts.product_typedomain_products.product_type is now the authoritative vocabulary

ContextStoreService.update() calls _validate_stage(stage_value) before acquiring the per-case lock whenever a "stage" key is present in the patches dict. The validator issues a single JOIN against domain_stages for the active domain (default wealth_management) and raises ValueError for any stage code not defined there.

The practical effect: the DB now accepts any string for current_stage and status, so a new domain can introduce its own stage codes (e.g. DEPOSIT_REVIEW) without a schema migration. Wealth-domain stages continue to be enforced — but by the domain_stages rows, not a hardcoded enum. The lifecycle constraints on CaseProduct / CaseProductStep (PENDING / IN_PROGRESS / COMPLETE / FAILED / SKIPPED) are intentionally kept as DB CHECKs — that vocabulary is not domain-configurable.

Open Gaps & Recommendations

  • Collect-once documents — current system re-requests shared docs per product; FR-DM-01/02/03 deferred to Phase 4.5 (skipped in this run) or a future phase
  • Multi-domain case isolation fully in place — onboarding_cases.domain_id (migration 0029) stamps every case with its domain; list_cases scopes results by the user's persona membership; admin sees all domains. Retail/Deposit domain (retail_deposit) is live via the admin portal (Phase 11 ✅).
  • Framework/domain package boundary not extracted — CADF framework code and wealth-domain seed data are co-located; Phase 12 will separate them into distinct packages so new domains can be delivered as data-only drops
